# TavernVault 高层架构评审

> 评审日期：2026-09-01 · 对应版本 v0.4.3 fix-1（commit 8cc86ee）
> 评审范围：README、docs 全部文档、目录结构、csproj/slnx，以及 ApiServer / Vault / SettingsStore / FileOperations / CharacterCardFile / PngChunkIO / App 外壳的结构性抽查（非逐行评审）。
> 评审立场：严格审查者，优先缺陷与风险。

---

## 1. 总评

**这是一个架构意识明显高于同规模个人项目平均水平的代码库，但已出现"文档很丰满、验证有盲区"的失衡。**

值得肯定的：

- **分层干净**：Core（无 UI 依赖、可单测）与 App（外壳 + API + 前端）职责清晰，Core 可直接复用做 CLI 的预留是真实成立的。
- **写路径设计有防御意识**：备份→写盘→重扫的统一链路、回收站删除、酒馆源 403 护栏 + 强制备份、`GuardUnderRoots` 路径防护（前缀比较正确补了分隔符，不是裸 StartsWith）、`JsonNode` 无损编辑策略、索引版本门控——这些都是踩过坑才会有的设计。
- **PNG 块读写用临时文件 + File.Replace 原子落盘**，增量扫描复用、Id 路径哈希与用户数据迁移的因果关系想清楚并写进了文档。
- 测试不是摆设：41 项单测覆盖最容易踩坑的 CharacterBook 双向映射，冒烟脚本夹具自足。

但严格地看：

- **一个 v0.3.0 引入的静默数据损坏 bug 存活至今且已发布**（见下 2.1，本次评审已实测复现），直接违反项目自己的第一设计哲学（"用户资源是圣域"）。
- **本地 API 的信任模型停留在"绑 127.0.0.1 就安全"的层面**，对浏览器 drive-by / CSRF 没有任何防护（见 2.2）。
- **测试金字塔缺了"真实 PNG"这一层**：全部夹具是 JSON 卡，导致 PNG 专属路径（另存为、缩略图、块重写）回归无保护——2.1 的 bug 正是从这个缺口漏出去的。
- **文档之间已经开始互相矛盾**（测试数 36/41、冒烟 49/61 各文档不一；版本号 0.4.1/0.4.2/0.4.3.1 并存；"待提交"的改动实际已提交）。文档是本项目强项，但也是接下来最先腐化的资产。
- 单实例无防护（双开两进程共享 index.json，内存态分叉、最后写者胜）、`SaveSettings` 直接写文件而 `SaveIndex` 走 tmp+move 原子写——持久化可靠性不一致。

结论：**架构骨架健康，不需要重构；需要的是把"验证"和"安全边界"补到与"设计"同等的高度。**

## 2. 最严重的问题（5 条）

### 2.1 【数据损坏·已实测复现】PNG 角色卡"另存为"产出无图像的坏文件

`src/TavernVault.App/Hosting/ApiServer.cs:217-222`，`/api/cards/{id}/saveas` 对 PNG 卡片的执行序列是：

```csharp
File.Copy(item.FullPath, newPath);                 // ① 复制原图 ✔
await File.WriteAllTextAsync(newPath, cardNode.ToJsonString(...)); // ② 用 JSON 文本覆盖刚复制的 PNG ✘
CharacterCardFile.Save(newPath, cardNode);         // ③ 按 .png 扩展名走 WriteTexts
```

步骤②把 PNG 字节流截断成了 JSON 文本；步骤③ `PngChunkIO.WriteTexts` 在非 PNG 内容上枚举不到任何块（签名不匹配直接 `yield break`），最终写出的文件 = **PNG 签名 + chara/ccv3 两个 tEXt 块，IHDR/IDAT/IEND 全部丢失**。

评审时用真实 Core 库按该序列实测：

| 文件 | 大小 | IHDR | IDAT | IEND | 被索引为角色卡 |
|---|---|---|---|---|---|
| 原文件 | 191 B | ✔ | ✔ | ✔ | ✔ |
| saveas 产物 | 267 B | **✘** | **✘** | **✘** | **✔（！）** |
| 对照组（①+③，无②） | 348 B | ✔ | ✔ | ✔ | ✔ |

**最恶劣之处在于静默性**：产物签名合法、chara 块可读，`CharacterCardFile.Load` 正常返回，重扫后在应用里显示为一张完全正常的卡片。用户直到把"副本"导入酒馆发现没有图像时才会察觉，而此时用户可能已删除原卡。该 bug 自 v0.3.0（另存为功能上线）起存在于每个已发布版本。

**遗漏原因**：冒烟与单测夹具全部是 JSON 卡（`tests/smoke_api.py` 的 `测试卡.json`），PNG saveas 路径零覆盖。
**修复**：PNG 分支只保留 ①+③（或：②仅在目标为 .json 时执行——而 JSON 分支 Save 本就会写文本，②可直接删除）。一行级改动。

### 2.2 【安全】本地 API 无任何调用方校验：浏览器 drive-by 可删除/改写用户文件

`ApiServer` 的全部 31 个端点不校验任何调用方身份：无令牌、无 `Host` 白名单（DNS rebinding）、无 `Origin` 检查。"只绑 127.0.0.1"防得住局域网邻居，**防不住用户浏览器里的任意网页**——跨域 POST（`no-cors` fetch、表单提交）不需要 CORS 预检就能把请求送达并触发副作用，响应读不到无所谓。

攻击链是完整闭环的：

1. 恶意网页 `POST /api/roots` 把 `C:\Users\<name>\Documents` 注册为库根（`AddRoot` 只要求目录存在）；
2. `POST /api/rescan` 触发索引；
3. 条目 Id = 路径哈希，算法随源码公开，可预测；
4. `POST /api/items/{id}/delete` 把任意文件送进回收站，或 `PUT /api/text/{id}` 改写配置类文件。

窗口模式的随机端口只是弱缓解（网页可端口扫描）；`--server` 模式固定 47999 且 `server-url.txt` 落盘，等于明示。对一个主打"保护用户资源"的工具，这是定位级的矛盾。

**修复**：启动时生成随机会话令牌，经 WebView2 注入前端，Kestrel 中间件校验自定义 header（浏览器跨域无法伪造自定义 header 而不触发预检）；同时校验 `Host` 仅允许 `127.0.0.1`/`localhost`。

### 2.3 【可靠性】备份失败静默 + 全程序零日志：安全网可能已失效而无人知晓

`Vault.BackupBeforeWrite` 注释明写"失败不抛出"（`Vault.cs:68`）；`BackupStore` 内部失败同样不外显。叠加现实场景——用户把备份目录自定义到某个可移动盘/已满分区（v0.4.1 起支持任意位置）——**备份链路断裂后：写入照常进行、UI 照常提示"保存成功"、酒馆源强制备份的承诺照常写在文档里，但磁盘上一个备份都没有。** 用户发现时通常是需要还原的那一刻。

全局唯一的错误出口是启动失败 MessageBox 和 `DispatcherUnhandledException` 弹窗（`App.xaml.cs`）；Kestrel 请求异常被 `Handle/HandleAsync` 包装成 400/500 后没有任何落盘记录。无日志文件、无崩溃转储、无"最近错误"界面。

**修复**：数据目录下滚动日志（最简单的 `File.AppendAllText` + 日期切分即可）；备份失败时写操作响应带 `warning` 字段，前端显性提示"本次保存无备份兜底"。

### 2.4 【可维护性】文档数字与状态已开始漂移，且无单一事实源

评审当天实测的矛盾（非穷举）：

| 事实 | README | development-handoff | quick-reference | 实际 |
|---|---|---|---|---|
| 单测数 | 36 项 | 41 项 | 36 项 | 41（7 个测试类合计） |
| 冒烟数 | 49 项 | 61 项 | 49 项 | 61 |
| 当前版本 | — | §7 写"当前 0.4.1" | 对应 v0.4.3 fix-1 | csproj 0.4.3.1 |
| v0.4.3 fix-1 状态 | — | §9.2"待提交" | — | 已提交（8cc86ee） |
| handoff 页脚 | — | "对应 v0.4.2" | — | 页首写 v0.4.3 fix-1 |

版本史同时维护在 README 表格、handoff §9、架构图 §11 三处。fix-1 刚确立了"文档演进规则"，但规则管得住新增条目，管不住散落在各处的**存量数字**。项目把"任何新接手的 agent 读完文档即可继续开发"作为文档目标——数字漂移恰恰是这个目标最大的腐蚀剂。

**修复**：测试数、当前版本在 docs 里一律改为"以 `dotnet test` 输出 / csproj `<Version>` 为准"，版本史收敛到 README 一处（其余引用）；或用 pre-commit 脚本从 csproj 生成。

### 2.5 【稳定性】写路径无并发防护，且每次写都同步全量 Rescan

- `PUT /api/cards/{id}` 等编辑端点是 读→改→备份→写→重扫 的多步序列，**跨步骤无锁也无版本/ETag**：两个编辑器标签页（或窗口 + 另一终端调 API）同时保存同一张卡，后写覆盖先写，丢失一次编辑。备份能还原磁盘内容，但用户不知道发生过覆盖。
- 每次写操作后同步 `vault.Rescan()`：增量复用省了解析，但仍是 O(库文件数) 的目录枚举 + stat，且持有 `_lock` 串行化所有并发请求。库到几万文件量级时，每次保存的尾延迟会显性化。
- 附带：无单实例防护。双开 exe = 两个 Kestrel + 两个内存 Vault 共享同一 `index.json`/`settings.json`，互相覆盖丢更新；`SaveSettings` 本身还是非原子直写（`SaveIndex` 倒是 tmp+move），崩溃窗口内可能截断 settings。

**修复**：编辑端点加条目级并发令牌（前端保存时带回读取时的 `modifiedAt`，不匹配则 409）；写后重扫改为按单文件增量更新索引而非全量 Rescan；启动加命名 Mutex 单实例；`SaveSettings` 对齐 `SaveIndex` 的原子写法。

## 3. 最优先的优化方向（5 条）

1. **修 2.1，并把"真实 PNG 夹具"钉进测试体系**。单测已有 `TestPng` 辅助，照此在 `smoke_api.py` 生成最小 PNG 卡，覆盖三条 PNG 专属路径：另存为（断言产物含 IDAT）、编辑保存（断言图像块字节级不变）、缩略图生成。这一条堵住的不只是当前 bug，而是"PNG 路径永远靠手工验证"的结构性缺口。
2. **给本地 API 加会话令牌 + Host 校验**（2.2 的方案）。工作量约半天，消除的是项目唯一的远程攻击面。顺手把 `--server` 模式的 `server-url.txt` 改为 `server-connection.json`（url + token），脚本化场景兼容。
3. **备份链路可观测化**：失败显性化（响应 warning + UI 提示）+ 数据目录滚动日志 + 设置弹窗里"备份健康度"（上次成功备份时间、目录可写性探测）。备份是这个项目的信任根基，根基需要仪表盘。
4. **文档收敛**：数字只留单一事实源（csproj / 测试命令输出），docs 引用而不复制；版本史只留 README 一处；把 §9.2 这类"工作区状态"段落从长期文档移到 commit message 或 CHANGELOG.md。每次发版跑一次"数字一致性检查"（可以是 smoke 脚本里加三项断言）。
5. **冒烟测试进程内化，进 `dotnet test`**。当前 smoke_api.py 需要手工"先起服务、注意 Git Bash 路径转义、再跑脚本"两步走，无 CI 可挂。用 `WebApplicationFactory`/`TestServer` 把 61 项冒烟变成 `dotnet test` 的一部分，是为将来拆分 985 行的 `editor.js`、701 行的 `ApiServer.cs` 准备的安全网——**先补网，再拆分**，顺序不要反。

## 4. 当前最缺少的文档或信息（3 条）

1. **安全威胁模型**：README 只有一句"只绑定 127.0.0.1"。缺一页明确声明：信任边界在哪（本机任意进程？浏览器？同机其他用户？远程桌面会话？）、哪些攻击面被接受、哪些被防御。2.2 的修复完成后，这页文档就是它的事实依据。
2. **发布与分发说明**：仓库没有任何打包/发布文档——framework-dependent 还是 self-contained？WebView2 运行时的真实前置条件（README 说 Win10/11"自带"，但早期 Win10 与精简镜像并没有，MainWindow 里那个兜底弹窗说明作者知道）？用户升级时数据/索引/备份如何迁移？目前发布流程只存在于维护者脑子里。
3. **故障恢复操作手册**：备份目录不可写/磁盘满/manifest.json 损坏/索引损坏时分别会发生什么、用户怎么自救。2.3 指出的静默失败语义目前只存在于代码注释（"失败不抛出"），文档只字未提。

## 5. 如果只能先做一件事

**修复 PNG 另存为的数据损坏 bug（删掉 `ApiServer.cs:220-221` 那次多余的 `WriteAllTextAsync`），同时在冒烟测试里加一个真实 PNG 夹具断言产物含 IDAT。**

理由：这是全部发现中唯一一个**已发布、确定性触发、静默损坏用户数据**的缺陷，直接违反项目"用户资源是圣域"的第一原则；修复是一行级改动，回归测试约二十行；而它继续存活的每一天，都有用户拿坏掉的"副本"替换掉好原卡的风险。安全加固（2.2）紧随其后——但它需要设计决策，而这个 bug 只需要删除。
