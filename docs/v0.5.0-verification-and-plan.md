## 二、本轮新发现

### N1【高·确定性产品缺陷】备份已达保留上限时，还原"最旧"备份必然失败

`BackupStore.Restore`（BackupStore.cs:139-155）的执行序：

1. `File.Exists(PathFor(info))` 检查源备份存在 ✔
2. **还原前安全备份当前文件** → `BackupBeforeWrite` 追加第 6 条 manifest 记录 → `PruneLocked` 按"每文件最多 5 份"轮转，**删除最旧的一份 = 正在被还原的那条的物理文件**
3. `File.Copy(PathFor(info), …)` → 源已被上一步删除 → `FileNotFoundException` → 400

探针实测（同一文件连续 6 次编辑堆满保留窗口后还原最旧备份）：

```
还原最旧(2026-09-01T22:41:08.628) → {'error': "Could not find file
  '...\\backups\\b90f31786d13-20260901-224108-图像卡.png'."}
还原后 description = '版本5'  (期望 '版本0')
```

- **UI 完全可达**：编辑同一张卡 5 次后，在备份列表点"最早"那份（最典型的"回到最初版本"操作）。
- **来源**：v0.3.0 引入，非 v0.5.0 新增；但 v0.5.0 增量更新让保存提速一个数量级，短时间堆满 5 份的概率大增。
- **为何此前没测出**：冒烟始终在新鲜数据目录上跑，还原点之前该文件备份从未到过上限（干净首跑实测还原点仅 2 份）。
- 失败模式是显式 400 报错，**不是静默损坏**（文件名含 Id，同秒备份不会别名冲突——这一点已排除）。

**修复方案**（三选一，推荐 ①）：
1. `Restore` 开头先把源备份读入内存（或复制到临时文件），再做安全备份，最后从内存/临时副本写回原路径；
2. `PruneLocked` 增加"排除正在还原的条目"参数；
3. 还原的安全备份**不触发轮转**（该次备份允许临时超限，下次正常备份时再收敛）。

配套回归测试：单测一条（写满 5 份 → 还原最旧 → 断言成功且内容正确）；冒烟一条（同样场景，当前冒烟在干净目录上永远到不了上限，需要用 API 直接堆满）。

### N2【中·测试缺陷】冒烟脚本的备份目录清理路径双层嵌套，清理是空操作

smoke_api.py 清理段：

```python
bk_dir = os.path.join(os.path.dirname(os.path.abspath("testdata-server/server-connection.json")),
                      "testdata-server", "backups")
```

`dirname(abspath(...))` 已经是 `...\testdata-server`，再 join `testdata-server/backups` 得到 **`testdata-server\testdata-server\backups`（不存在）**，`rmtree(ignore_errors=True)` 静默无效。后果：同一数据目录连续跑两次冒烟，上一轮残留把该文件备份顶到保留上限，**稳定触发 N1**（本轮的 3 个 FAIL 正是这样发现的）。

**修复**：直接 `os.path.join(os.path.dirname(conn_path), "backups")`；或更根本地——规定冒烟必须配全新数据目录（脚本启动时检测 `server-connection.json` 已存在即提示先清理并重启服务）。同时把 `testdata/`、`testdata-server/` 加入 `.gitignore`（当前未忽略，`git status` 出现未跟踪目录）。

### N3【低·代码缺陷】单实例 Mutex：第二实例退出路径抛异常；且锁粒度与提示语不符

- `App.OnExit` 无条件 `_singleInstance?.ReleaseMutex()`——第二实例路径（`createdNew=false`）线程**不拥有**该 Mutex，`ReleaseMutex` 抛 `ApplicationException`。修复：仅 `createdNew` 时 Release（或 try/catch，或干脆不 Release——进程退出 OS 自动释放）。
- Mutex 名 `Local\TavernVault.SingleInstance` 不区分数据目录：窗口模式在跑时，开发者无法再起 `--server` 实例跑冒烟（**文档化的测试工作流被阻断**）；而提示语却说"同一数据目录只允许一个实例"。建议 Mutex 名掺入 DataDir 的稳定哈希，与提示语对齐。

### N4【低·文档与行为不一致】move 端点没有 BackupBeforeWrite，架构图却画了

架构可视化 §8 决策树对 rename 与 move 都画了 BK（备份）步骤；实际 `POST /api/items/{id}/move` 不备份。跨根移动虽不覆盖文件，但误移动后原位置无副本可回。二选一：给 move 补备份（与"先备份 → 写盘"哲学对齐），或改图并在 README 明确"移动不产生备份"。

### N5【中·UX 缺口】409 之后前端没有可用的恢复路径

`CheckNotModified` 返回 409 后，editor.js 只 toast 错误。quick-reference 指引用户"重新打开该条目再保存（会重扫索引）"，但实测前端 `openDrawer(id)` 直接渲染**缓存的 items 数组**，不重取 `/api/items/{id}`、也不触发 rescan——重新打开后 `modifiedAt` 仍是旧值，再次保存**仍然 409**，用户被锁死在冲突状态（唯一出路是手动点"重新扫描"）。

**修复**（任选）：drawer 打开时按 id 重取该条目再渲染；或保存收到 409 时前端自动 `POST /api/rescan` + 重取该条目 + 提示"文件已更新，请确认后重新保存"。

### N6【低·文档漂移复发】handoff §9.2 仍写"v0.5.0 工作区改动待提交"

实际已提交（c63c8aa）。上一轮刚立的规矩（状态段不进长期文档）没执行到位——建议把 §9.2 的"当前状态/待提交"整段移出 handoff（commit message 或 CHANGELOG），长期文档只留版本表。

### 其他记录（不单独立项）

- `?token=` query 会随缩略图请求进入 WebView2 HTTP 缓存/内存——同配置文件内残留，威胁模型内可接受（README 已声明），无需处理。
- `Restore` 的 `File.Copy` 直接覆盖原文件，中断可产生半写文件；顺手改 tmp+`File.Replace` 与 PngChunkIO 同款原子落盘（与 N1 修复同一次改动内做掉）。
